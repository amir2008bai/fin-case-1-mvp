# Шпаргалка для 2-минутного демо и ответов жюри (FinTech, трек 1)

Все числа ниже взяты из `README.md`, `docs/protocol.md`, `PROJECT_STATUS.md` и реального прогона `python -m audit_env verify` на версии генератора 2.1.0. Рядом с каждым числом указана команда, которая его воспроизводит.

## 1. Сценарий 2-минутного демо

### 0:00–0:25 — Суть решения и запуск единой проверки
- **Что сказать:** «Мы построили воспроизводимую офлайн RL-среду для ИИ-аудитора на Python 3.11 без внешних зависимостей, сети и GPU. Среда моделирует полный цикл учёта компании за месяц (услуги по актам Р-1 и товары по накладным З-2, валюты KZT/USD/RUB, НДС 16 % «в т.ч.»), даёт агенту 5 инструментов и проверяет ответы независимым детерминированным оценщиком».
- **Команда:**
  ```bash
  python -m audit_env verify
  ```
- **Что показать на экране:** 10 разделов проходят одной командой (около **45 с** и около **400 МБ** памяти, зависит от машины): **212 тестов OK**, **22/22** проверки контракта/изоляции/награды, **60** случайных конфигураций независимой проверки эталона (`0` сбоев), **187 файлов `data/`** байт в байт совпадают с регенерацией, red team (`violations: none`), экономия шагов (`violations: none`) и контроль утечек на **360** закрытых эпизодах (`violations: none`).
- **Скорость и размер:** генерация эпизода **14–60 мс**, шаг `step` **11–17 мкс**, полный аудит эпизода **2–6 мс**, репозиторий **17.7 МБ**, код **0.45 МБ**, внешних зависимостей нет.

### 0:25–0:55 — Изоляция и закрытый контейнер агента
- **Что сказать:** «Закрытые эпизоды генерируются только на секретном ключе (`Config.keyspace = "secret"` по умолчанию), который не передаётся процессу агента (`runner.agent_environment`). Оценщик работает снаружи, а агент — в отдельном read-only контейнере без сети, где нет генератора, оценщика и ответов».
- **Команды:**
  ```bash
  make docker-verify
  python -m audit_env demo --closed --policy expert --agent-image fintech-audit:agent
  ```
- **Что показать:** закрытый запуск возвращает точные TP/FP/FN, F1 и награду только оценщику; в наблюдениях агента нет ни эталона, ни seed, ни терминальной награды (`reward = None` в закрытом режиме).

### 0:55–1:30 — Устойчивость награды (Red Team и утечки)
- **Что сказать:** «Мы проверили оценщика против 12 нечестных стратегий, перебора 200 000 seed и статистического аудита утечек».
- **Команды:**
  ```bash
  python -m audit_env attacks
  python -m audit_env leakage
  ```
- **Что показать:**
  - `python -m audit_env attacks` (108 закрытых эпизодов, 360 ошибок): `honest` получает **+0.959** на книгах с ошибками, `silence` — **+1.000** на чистых; ни одна из 12 атак (`flag-all`, `shortcut`, `type-hedge`, `amount-hedge`, `repeat-farming`, `noise-plus-honest`, `evidence-stuffing`, `evidence-padding`, `id-guess`, `persuasion`, `stall`) не обходит честную работу и молчание; перебор **200 000 seed** находит seed на открытом ключе и не находит на секретном.
  - `python -m audit_env leakage` (360 закрытых эпизодов): 8 признаков оформления в пределах **±0.06** от 0.50, 4 структурные приметы в пределах **±0.08** от 0.50, `violations: none`.

### Если есть экран: веб-интерфейс (по ТЗ баллов не даёт, только для наглядности)
- **Команда:** `python -m audit_env serve`, затем открыть `http://127.0.0.1:8765/`.
- **Что показать:** создать эпизод «Все 6 типов + 2 взаимодействия», запустить `expert` (награда и F1 видны в открытом режиме), кликнуть по доказательству в выводе и перейти к строке книги или документу; затем запустить `flag-all` и показать отрицательную награду; в закрытом режиме оценка остаётся у оценщика.

### 1:30–2:00 — Градиент сложности, экономия шагов и диагностика LLM
- **Что сказать:** «При росте сложности и числа законных «двойников» простые эвристики проваливаются, недочитывание книги всегда проигрывает, а диагностический прогон настоящих LLM через встроенный MCP-сервер показывает реальный градиент сложности».
- **Команды:**
  ```bash
  python -m audit_env benchmark --curriculum --repeats 5
  python -m audit_env economy
  python -m audit_env jury
  python -m audit_env mcp --compact
  ```
- **Что показать:** на `benchmark --curriculum --repeats 5` (90 эпизодов) простая сверка `reconcile` падает с F1 **0.204** (`easy`) до **0.075** (`hard`), число ложных срабатываний растёт с **5.5** до **21.8** на эпизод; на `economy` (108 эпизодов) пропуск одной страницы экономит `0.002` награды и теряет в среднем **0.16** (`+0.960` → `+0.803`).

### Прогон LLM (диагностика из `README.md`)
Команда воспроизведения:
```bash
python -m audit_env llm-probe --provider openai --model <модель> --base-url <OpenAI-совместимый URL> \
  --episodes 5 --same-episodes --report <файл.json>
```
Отчёты лежат в `docs/llm_probe/`. Все модели видят одни и те же 5 закрытых эпизодов шаблона жюри (`holdout-01`, `holdout-11`, `holdout-13`, `holdout-17`, `holdout-06`):

| Модель | Эпизодов | Ошибок найдено | Ложных выводов | F1 | Награда | Шагов |
|---|---|---|---|---|---|---|
| `deepseek-flash` (DeepSeek-V4.1-Flash) | 5 | 9 из 13 | 2 | 0.82 | +0.54 | 48 |
| `gemini-3.5-flash-lite` | 5 | 0 из 13 | 0 | 0.20 | −0.60 | 10.6 |
| `gemini-3.5-flash` | 1 (чистый) | — | 0 | 1.00 | +0.98 | 10 |
| `nemotron-3.5-lightning` | 1 (чистый) | — | 7 | 0.00 | −1.00 | 6 |

Это диагностика на пяти эпизодах, а не оценка моделей: сильная LLM находит большую часть ошибок, но промахивается на взаимодействиях, лёгкая сдаётся с пустым ответом, а торопливая на чистой компании получает −1.00 за 7 ложных обвинений.

## 2. Ответы на 15 вероятных вопросов жюри (по критериям раздела 10 ТЗ)

### Блок А. Контракт и изоляция (25 баллов)

**1. Как гарантируется, что агент не может подсмотреть эталон, seed или награду в закрытом режиме?**
- В закрытом режиме (`AuditEnv(training=False)`) терминальная награда в ответе агенту равна `None`, а `truth.json` и `provenance.json` не попадают в наблюдения (проверка `no truth leaks to observations`, `python -m audit_env verify`, раздел 2).
- `Config.keyspace` по умолчанию равен `"secret"`, и закрытый режим принудительно использует секретный ключ (`tests/test_adapter_isolation.py`). Переменные `AUDIT_ENV_SECRET` и `AUDIT_ENV_KEY_FILE` удаляются из окружения подпроцесса агента (`runner.agent_environment`), а физическая граница изоляции — контейнер агента (`make docker-agent`), в образ которого не копируются генератор, оценщик и ответы.

**2. Что происходит при некорректных действиях, обрыве агента, превышении 100 шагов или 60 секунд?**
- Ошибки инструментов (`invalid_action`, `unknown_table`, `unknown_id`, `invalid_limit`, `invalid_cursor`, `invalid_expression`, `reset_required`, `episode_finished`) возвращают ограниченное JSON-сообщение с кодом ошибки, расходуют шаг и дают награду `0.0` (проверка `bounded errors cost a step`, `python -m audit_env verify`, раздел 2).
- Лимиты оцениваемого прогона — **100 шагов** (100-й шаг может быть только `submit`) и **60 секунд** (`AuditEnv`, `runner.py`). При обрыве выставляется `truncated = true`, пустой ответ оценивается по формуле (на чистых книгах `1 − 0.002·steps`, на книгах с ошибками `−1`). Нарушение схемы `submit` или сбой протокола агента дают `−1.0`. Интерактивные адаптеры UI (1 час) и MCP (30 мин, `--timeout`) поднимают только часы через `interactive=True`, сохраняя лимит 100 шагов и все правила.

**3. Как устроены 5 инструментов и есть ли риск выполнения произвольного кода в калькуляторе?**
- Контракт включает ровно 5 инструментов: `list_records` (до **50** строк на страницу, стабильные курсоры, привязанные к таблице и эпизоду), `get_record`, `get_document`, `calculator` и `submit` (`docs/protocol.md`).
- Калькулятор принимает только символы `0-9 . + - * / ( )` и пробелы и считает через `Decimal` (50 знаков), без `eval`, степеней и произвольного кода (проверка `calculator: decimals only`, `python -m audit_env verify`, раздел 2; `tests/test_fuzz.py`).

### Блок Б. Данные и эталон (25 баллов)

**4. Как вы доказываете, что эталон корректен и не содержит «фантомных» ошибок?**
- Ошибки внедряются не правкой таблиц напрямую, а как причинные переопределения решений в чистом сбалансированном мире (`world.py` → `books.py` → `scenarios/`), с записью «до/после» и хэша чистой книги в `provenance.json`.
- Независимый аудитор `checks.py` читает только публичные таблицы и `policy.json`: на чистой книге (восстановленной из `provenance.json`) он находит **0** ошибок, на грязной — ровно эталон `truth.json`. В `python -m audit_env verify` (раздел 3) это проверяется на **60** случайных конфигурациях (`failures: 0`), а отдельно доступно на любом N через `python -m audit_env selfcheck --n 300`.

**5. Откуда взяты данные? Есть ли в репозитории реальные финансовые документы?**
- Все компании, клиенты, счета, платежи и суммы полностью синтетические (`README.md`, раздел «Откуда взяты параметры генератора»). Реальные документы, реквизиты, БИН и банковские выписки в репозиторий и в сдачу не входят; автоматический тест гигиены `tests/test_episode_io_hygiene.py` (`python -m audit_env verify`, раздел 1) проверяет отсутствие реальных банковских данных в отслеживаемых файлах.

**6. Насколько реалистичны ошибки и есть ли законные «двойники», чтобы задача не сводилась к простому фильтру?**
- Поддержаны **4 обязательных типа** (`duplicate_invoice`, `payment_allocation`, `fx_rate`, `period_cutoff`), **2 взаимодействия** (`fx_boundary_payment`, `fx_partial_allocation`) и **2 дополнительных типа из практики** (`vat_on_top`, `uncollected_service`, по умолчанию выключены).
- Для каждого типа есть законные «двойники» (предоплаты, переплаты, курсовые разницы 6250/7430, акты после конца периода, повторяющиеся абонплаты и т.д.). В результате простая сверка `reconcile` получает отрицательную награду на всех категориях шаблона жюри: чистые **−1.000**, одна ошибка **−0.506**, смесь **−0.381**, взаимодействия **−0.632** (`python -m audit_env benchmark --holdout --repeats 5`, 100 эпизодов, 340 ошибок).

### Блок В. Надёжность награды (25 баллов)

**7. Можно ли взломать награду массовыми обвинениями, повторами или перебором вариантов?**
- Нет. Формула `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)` использует максимальное взаимно однозначное паросочетание (`scoring.py`), неизвестный тип и повторы считаются FP.
- На `python -m audit_env attacks` (108 закрытых эпизодов, 360 ошибок) `flag-all` получает **−1.000** (3 240 FP), `type-hedge` **−0.480** (1 500 FP), `amount-hedge` **−0.043** (708 FP), `repeat-farming` **+0.292** (360 FP), `noise-plus-honest` **+0.149** (540 FP) против **+0.959** у честного аудитора (`honest`) и **+1.000** у молчания (`silence`) на чистых книгах.

**8. Можно ли угадать ID, подсунуть посторонние доказательства или «уговорить» оценщика текстом?**
- Нельзя: `evidence_ids` проверяются на то, что каждый ID был реально показан агенту в этом эпизоде (`seen`), относится к данной ошибке (`relevant_ids`) и покрывает один из допустимых наборов доказательств (`evidence_sets`). В `python -m audit_env attacks` стратегии `id-guess`, `evidence-stuffing` и `evidence-padding` получают **−1.000** на книгах с ошибками.
- Поле `explanation` (до 1000 символов) на оценку не влияет: `persuasion` и `persuasion-plain` получают идентичную награду в каждом из 108 эпизодов (`python -m audit_env attacks`).

**9. Не подталкивает ли штраф за шаги (`−0.002`) агента недочитывать книгу ради экономии?**
- Нет. По замерам `python -m audit_env economy` (108 закрытых эпизодов) пропуск даже одной последней страницы экономит `0.002`, но снижает среднюю награду на **0.16** (`+0.960` → `+0.803`, появляется 11 FP и 34 FN), а чтение 50 % книги роняет награду до **+0.144**. При этом самые большие допустимые книги (~1 940 строк, 89 счетов, 72 оплаты) читаются целиком за **48 шагов из 100** (`python -m audit_env economy`).

### Блок Г. Воспроизводимость и обобщение (15 баллов)

**10. Воспроизводятся ли эпизоды, таблицы и датасет на другой машине?**
- Да. Одинаковые `seed`, `config`, ключ, версия и действия воспроизводят записи, переходы и награды байт в байт (`test_files_are_byte_identical_across_hash_seeds`, `python -m audit_env verify`, раздел 1 и 2).
- Закоммиченная папка `data/` (10 train + 10 dev эпизодов, ответы, траектории, `SHA256SUMS` — всего **187 файлов**) проверяется на побайтовое совпадение со свежей генерацией в разделе 4 `python -m audit_env verify`. Таблицы `benchmark`, `jury`, `attacks`, `economy` и `leakage` по умолчанию выводят секретный ключ из `--seed`, поэтому воспроизводятся точно.

**11. Защищена ли среда от переобучения на ID, порядок строк и статистические приметы (shortcuts)?**
- Все ID непрозрачны и порождаются HMAC от секретного ключа (`render.py`, `keys.py`); парные проверки со сменой ID и перемешиванием порядка строк сохраняют ответы (`paired ID/order transform`, `python -m audit_env verify`, раздел 2 и 5; `python -m audit_env jury`).
- Раздел 10 `python -m audit_env verify` (отдельно `python -m audit_env leakage`) на **360 закрытых эпизодах** проверяет AUROC по **8 признакам оформления** (позиции строк, биты HMAC-ID, секунды меток времени — порог **±0.06**, фактический макс. дрейф `0.0132` в контрольном прогоне) и **4 структурным приметам** (`goods_waybill`, `cited_by_receipt`, `receipt_lag_days`, `customer_invoices` — порог **±0.08**, фактический макс. дрейф `0.0427`, `violations: none`). При этом мы честно фиксируем в `README.md`, что аудит страхует от перечисленных шорткатов, а не доказывает отсутствие любых возможных утечек.

**12. Что на самом деле показывает модель `micro`? Вы заявляете, что RL улучшил модель?**
- Нет, и мы это честно подчёркиваем в `README.md` и `docs/micro-model.md`: `micro` — это логистический ранжировщик поверх кандидатов и признаков-индикаторов тех же опубликованных правил, что и `checks.py` (обучается на CPU за ~10 с на 120 эпизодах командой `python -m audit_env train`).
- На **290 закрытых эпизодах** трёх наборов (930 ошибок: `benchmark --holdout --repeats 5`, `--extended --repeats 10`, `--curriculum --repeats 5`) `micro` повторяет ответы `checks.py` без ложных срабатываний. Это доказывает работоспособность замкнутого цикла «среда → награда → обучение → закрытая оценка» на CPU, но не заявляет превосходства над правилами или улучшения LLM без контролируемого сравнения.

### Блок Д. Инженерия и объяснение (10 баллов)

**13. Укладывается ли решение в ограничения проверки: без сети, без GPU, 2 CPU, 4 ГБ RAM, <= 1 ГБ, read-only?**
- Да. В `pyproject.toml` нет ни одной внешней зависимости (только стандартная библиотека Python 3.11+). Замеры: генерация эпизода **14–60 мс**, шаг **11–17 мкс**, полный аудит эпизода **2–6 мс**, полный цикл `python -m audit_env verify` — около **45 с** и около **400 МБ** памяти; репозиторий весит **17.7 МБ**, код — **0.45 МБ**. Базовый Docker-образ `python:3.11.14-slim` закреплён по digest, а `make docker-verify` запускается с флагами `--network=none --read-only --cap-drop=ALL --cpus=2 --memory=4g`.

**14. Как подключаются внешние LLM-агенты и можно ли прогнать реальную LLM на закрытых эпизодах?**
- Среда поддерживает три интерфейса без внешних зависимостей: JSONL-протокол `runner.py` (Linux и Windows, без `select`), локальный HTTP API для UI (`python -m audit_env serve`) и стандартный MCP JSON-RPC 2.0 сервер по stdio (`python -m audit_env mcp`, в том числе `--compact`, который сжимает только страницы таблиц колонками без потерь, оставляя `policy` дословно).
- Для диагностики реальной LLM через `mcp_server.py` есть команда `python -m audit_env llm-probe` (5 закрытых эпизодов, ключ API только из переменной окружения и никогда не печатается; без сети или ключа корректно завершается с кодом 0). Результаты прогона 4 моделей приведены выше и в `docs/llm_probe/`.

**15. Какие ограничения и честные допущения есть у текущей версии 2.1.0?**
- Все ограничения явно перечислены в `README.md` (раздел «Честные ограничения»): одна компания и один месяц на эпизод, книга только в KZT (валюта только в документах), не моделируются документы, полностью не попавшие в учёт, и партионный учёт склада; `uncollected_service` строится на подписках, а валютные ошибки — на услугах иностранным клиентам; параметры генератора подобраны вручную по практике небольшой сервисной компании, их статистическая репрезентативность не проверялась.
