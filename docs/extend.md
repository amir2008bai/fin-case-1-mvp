# Как дать команде развивать проект

На старте разработчик запускает `make verify`, затем меняет один сценарий и добавляет проверку, которая пересчитывает расхождение по наблюдаемым записям. CI повторяет локальную команду в образе и проверяет обмен с отдельным контейнером агента.

Чистую бухгалтерскую историю строит `audit_env/history.py`. Каждый тип ошибки живёт в отдельном модуле `audit_env/scenarios/` и получает подготовленные записи. Модуль возвращает `Issue` и описание изменения. `generator.py` выбирает операции по конфигурации, применяет мутации и собирает эпизод.

## Пример: нераспределённая часть платежа

В чистой истории платёж на 90 000 минимальных единиц уменьшает задолженность на 90 000 и кредитует банк на 90 000. После мутации задолженность уменьшается на 60 000, 30 000 попадает на транзитный счёт, банковская проводка остаётся на 90 000. Бухгалтерская запись сбалансирована, но распределение нарушает политику компании. Проверяемый вывод включает ID платежа, 30 000, KZT, ID документа платежа и ID трёх строк проводок. При полном пропуске распределения строка задолженности отсутствует, а транзитная строка содержит всю сумму.

Эталон фиксирует расхождение и набор доказательств. Журнал изменения отдельно хранит запись до мутации и записи после неё. Тест сборки эпизода проверяет эти данные отдельно от кода начисления награды.

## Предлагаемое разделение работы

1. **Валюта и курсы.** Добавьте валютные разрядности, два разных курса на соседние даты, политику выбора даты и пересчёт с `Decimal`. Добавьте идентификатор FX-записи, одинаково доступный в API и экспорте. Закрепите смысл суммы вывода: разница между фактической и нормативной суммой в базовой валюте. Сохраните пример, где эквивалентные суммы в разных валютах верны.
2. **Периоды.** Введите первичный документ с наблюдаемой датой хозяйственной операции и правилами признания. Создайте соседний период и сценарии до и после полуночи. Отдельно зафиксируйте случай, когда UTC-дата отличается от локальной даты.
3. **Совместные ошибки и качество данных.** После слияния первых двух задач добавьте два сценария на одной операции. Например, частичное распределение с неверным курсом и валютное распределение с неверным периодом. Проверьте, что два вывода имеют свой размер расхождения и достаточные доказательства. Добавьте возвраты как законный контрпример.
4. **Проверка сборки.** Сохраните автоматический запуск тестов, повтор по seed, повтор после перестановки записей и смены ID, сравнение политик и отдельный запуск агента. Закрытые конфигурации держите вне открытых файлов и образа агента.

## Условия слияния нового сценария

- Тип объявлен в `contracts.py`, отдельный счётчик принимает 0, отключение сохраняет чистую историю.
- Чистые записи формируются до мутации. В эталоне есть сумма, валюта, затронутые ID, допуск и наборы доказательств. В provenance есть изменение до и после.
- Независимый тест выводит числовое расхождение из открытых записей. Чистый контрпример не должен давать ложного обвинения.
- Политика сверки или демонстрационный сценарий получает все доказательства через публичный API за 100 шагов. Oracle проходит пару «исходные записи / новые ID и порядок».
- Тесты и закрытый запуск проходят из корня. Если меняется контракт данных, обновите этот документ, версию схемы и сериализацию.

Перед конкурсной сдачей добавьте принятую командой лицензию и зафиксируйте версию релиза. Формат JSONL, функции оценки и разделение процессов позволяют разработчикам расширять данные без изменения механизма проверки.
