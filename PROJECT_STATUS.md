**Контекст:** хакатон, финансовый кейс № 1 (RL-среда для ИИ-аудитора). Сдача 22.11.2026 23:59 (Астана).

**Состояние MVP:** `python -m audit_env verify` зелёный примерно за минуту (в CI ~25 с): 82 теста, 22/22 проверки контракта/изоляции/награды, независимая проверка эталона по 6 типам, байтовая сверка `data/`, закрытый шаблон жюри, расширенный шаблон, уровни сложности easy/medium/hard, red team (12 атак + перебор seed) и экономия шагов. CI зелёный (Linux, Windows, контейнер, агент в изолированном контейнере). Открыто: подача для жюри; LLM-обвязка прототипа — по желанию.

## История

### 2026-11-21 (редкий сбой verify)

- CI по PR упал на Windows: раздел 3 `verify` случайно собирает 60 конфигураций, и примерно одна из 2 300 превышала лимит 12 ошибок → `ValueError`, то есть `verify` падал примерно в 1 из 39 запусков. Теперь `selfcheck.random_config` перетягивает набор ошибок, пока он не уложится в лимит; поток случайных чисел для прежних seed не изменился. Воспроизведено на старом коде (`seed_base=58`), регрессионный тест `test_random_configs_respect_the_issue_cap`.

### 2026-11-21 (текст задачи)

Теперь задача перечисляет все 6 и говорит, что ошибок может не быть; тест `test_task_and_policy_name_every_finding_type`. `data/` перегенерирован: изменились только траектории (первое наблюдение) и `SHA256SUMS`, эпизоды байт в байт те же.

### 2026-11-21 (экономия шагов)

- `ScanPolicy` читает каждую страницу один раз и пропускает курсы, если нет документов в валюте; `economy.py`, команда `economy`, раздел 9 в `verify`, `tests/test_economy.py`. Строки лежат в порядке непрозрачных ID, поэтому полное чтение — минимум для полного аудита: эксперт и модель тратят ровно его (0 лишних шагов на 108 закрытых эпизодах).
