# Финансовый кейс 1: RL-среда для ИИ-аудитора

**Кратко**
- Офлайн RL-среда для ИИ-аудитора: синтетическая компания за месяц (KZT/USD/RUB, НДС, акты и накладные), 4 обязательных типа ошибок из кейса и 2 из практики, 2 сценария их взаимодействия и законные «двойники».
- Одна команда: `python -m audit_env verify` — около 45 с, Python 3.11, без внешних пакетов, сети и GPU; тесты, 22 проверки контракта, независимая проверка эталона, байтовая воспроизводимость, атаки на оценщика, контроль утечек.
- Награду не обмануть: 12 нечестных стратегий (пометить всё, хеджирование типов и сумм, подбор ID, «уговоры» в тексте) и перебор 200 000 seed проигрывают честному аудиту и молчанию.
- Задача различает агентов: простая сверка — F1 0.20 → 0.08 от easy к hard, LLM находят от 0 до 11 ошибок из 13 на одних и тех же эпизодах, аудитор по правилам — все 13.
- Закрытый режим: эталон и награда остаются у оценщика, секретный ключ — только в его памяти, агент может работать в отдельном контейнере без сети и без ответов.

## Проверка одной командой

Нужен Python 3.11+. Внешние пакеты, сеть, GPU и платные API не нужны.

```bash
python -m audit_env verify
```

Команда последовательно:
1. прогоняет все тесты;
2. печатает 22 именованные проверки контракта, изоляции, награды и воспроизводимости;
3. доказывает корректность эталона на 60 случайных конфигурациях со свежим секретным ключом;
4. сверяет закоммиченные `data/` с регенерацией байт в байт;
5. гоняет 4 базовые политики и эксперта на шаблоне закрытой проверки (20 конфигураций, 5 чистых и 5 со взаимодействием, случайные seed), включая парные проверки со сменой ID и порядка;
6. делает то же на расширенном шаблоне: ошибки из практики и разные доли товаров;
7. делает то же на трёх уровнях сложности (easy → medium → hard, книги до ~2000 строк);
8. атакует оценщика 12 нечестными агентами и перебором seed ([Атаки на оценщика](#атаки-на-оценщика)) и падает, если хоть одна атака обходит честную работу или молчание;
9. проверяет [экономию шагов](#экономия-шагов): эксперт и модель не тратят ни одного лишнего шага (минимум — по ⌈строк/50⌉ страниц на нужную таблицу плюс отправка, поэтому число шагов растёт с размером книги: 11–17 на обычных, до 48 на самых больших), недочитывание книги всегда проигрывает, самые большие допустимые книги читаются целиком в пределах лимита;
10. проводит выборочный контроль утечек (`leakage`) на 360 закрытых эпизодах. Признаки оформления (позиция строки, биты HMAC-ID — по сути один признак, секунды меток времени) должны давать AUROC не дальше 0.06 от 0.50. Структурные приметы, по которым ошибку можно угадать без анализа (накладная или акт, есть ли оплата у счёта с услугой вне периода, срок оплаты, число счетов клиента), — не дальше 0.08: каждую сравнивают внутри той группы документов, где этот тип ошибки возможен. Это страховка от перечисленных шорткатов, а не доказательство отсутствия любых утечек.

Отчёт пишется в `build/verify-report.json`, при любом сбое код выхода ненулевой. Время около 45 с (CI сохраняет отчёт как артефакт каждого прогона).

### Контейнер (офлайн, 2 CPU, 4 ГБ, только чтение)

Ровно то, что делает `make docker-verify`; одна строка, поэтому работает в bash, PowerShell и cmd:

```bash
docker build --target verify -t fintech-audit:verify .
docker run --rm --pull=never --network=none --read-only --cap-drop=ALL --security-opt=no-new-privileges --cpus=2 --memory=4g --memory-swap=4g --pids-limit=64 --tmpfs /tmp:rw,nosuid,nodev,noexec,size=256m fintech-audit:verify
```

Базовый образ `python:3.11.14-slim` закреплён по digest. Сеть нужна один раз, чтобы `docker build` скачал его; сама проверка идёт без сети (`--network=none`). Для машины совсем без сети образ переносится через `docker save` / `docker load`.

Агент в отдельном контейнере: образ без генератора, без оценщика и без ответов, запуск `--network=none --read-only`. Оценщик остаётся снаружи и общается с агентом по JSONL.

```bash
docker build --target agent -t fintech-audit:agent .
python -m audit_env demo --closed --policy expert --agent-image fintech-audit:agent
```

`make docker-agent` прогоняет так агентов `expert`, `micro` и `inspector`. CI (`.github/workflows/verify.yml`) запускает `verify` на Python 3.11 в Linux и Windows, затем `docker-verify` и `docker-agent`, а отдельной задачей — Gymnasium-адаптер с установленным `gymnasium` (там пропуск теста считается сбоем).

## Что внутри эпизода

Эпизод — одна компания и один месяц, 200–2000 строк книги, 20–200 документов, 0–12 ошибок. Книга ведётся в KZT, есть клиенты из Кыргызстана (USD) и России (RUB).

Компания продаёт:
- **услуги** — подписки на ПО, сопровождение, внедрение, обучение; документ — акт выполненных работ (форма Р-1), для экспорта услуг — акт без НДС;
- **товары** — онлайн-ККМ, POS-терминалы, сканеры, принтеры, термолента; документ — накладная на отпуск запасов (форма З-2).

Доля товаров задаётся `config.goods_percent`; по умолчанию накладных примерно столько же, сколько актов. Учёт товаров:
- при отгрузке выручка и НДС проводятся так же, как по услугам, а себестоимость списывается со склада: Дт 7010 Кт 1330;
- закупки у поставщика: Дт 1330 и Дт 1420 (НДС к возмещению), Кт 3310;
- на начало периода есть остаток склада.

НДС 16 % включён в цену, к каждому документу с НДС выписан ЭСФ.

| Файл | Содержимое |
|---|---|
| `manifest.json` | `schema_version`, `episode_id`, `base_currency`, `period_start`/`period_end`, `timezone`, число записей и документов, разрядность валют, правила округления |
| `ledger.csv` | `row_id,timestamp,account,debit_minor,credit_minor,currency,entity_id,invoice_id,payment_id`. Отсутствующая связь записывается как `null` |
| `invoices.jsonl` | `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items`. В строках есть период услуги и НДС |
| `payments.jsonl` | `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs`. Если плательщик не указал счёт, `invoice_refs = null` |
| `fx.csv` | `date, source_currency, target_currency, rate, fx_id`. Курс — десятичная строка; четыре колонки кейса идут первыми в его порядке, `fx_id` добавлен последним, чтобы курс можно было цитировать как доказательство |
| `policy.json` | Все правила: границы периода, признание выручки, пересчёт валют, распределение платежей, НДС, правила выводов и доказательств |

Секретный ключ закрытых эпизодов (`keyspace: secret`) берётся из переменной `AUDIT_ENV_SECRET` (не короче 16 байт) или из файла, путь к которому задан в `AUDIT_ENV_KEY_FILE` (создаётся с правами 0600). Если не задано ни то ни другое, ключ живёт только в памяти процесса оценщика и на диск не пишется: у агента, запущенного тем же пользователем, нет файла ключа, который можно прочитать. Чтобы закрытые эпизоды воспроизводились между запусками или на другой машине, задайте `AUDIT_ENV_SECRET` явно. `AuditEnv().reset(seed)` по умолчанию работает на открытом ключе и воспроизводится везде.

Закрытые файлы оценщика: `truth.json` (тип, затронутые ID, сумма, валюта, допуск, допустимые наборы доказательств) и `provenance.json` (seed, конфигурация, отпечаток ключа, хэш чистой книги, причинные изменения «до/после»). Агент их не видит.

## Ошибки и ловушки

| Тип | Что ломается | Законные «двойники», которые не являются ошибкой |
|---|---|---|
| `duplicate_invoice` | Второй счёт на ту же услугу, клиента и период проведён в выручку (два менеджера выставили два счёта) | Та же абонплата в другом периоде, одинаковые цены у разных клиентов, многострочные счета |
| `payment_allocation` | Поступление по открытому счёту целиком или частично ушло в авансы 3510 вместо погашения 1210 | Предоплата до окончания услуги, переплата «с лишним нулём», оплата без ссылки на счёт, зачёт входящих авансов, разбитые и сводные оплаты |
| `fx_rate` | Счёт или поступление пересчитаны по курсу не той даты или по опечатанному курсу | Обычные курсовые разницы 6250/7430 на каждом валютном поступлении |
| `period_cutoff` | Выручка по услуге прошлого или следующего периода признана в этом; поступление после конца периода проведено в нём по дате в часовом поясе плательщика | Счета, выписанные позже за прошлый период; счета, выписанные после конца периода; метки времени, у которых дата «на стене» вне периода, а момент внутри |
| IX-A `fx_boundary_payment` | Частичная валютная оплата на границе периода: `period_cutoff` + `fx_rate` | |
| IX-B `fx_partial_allocation` | Часть валютного поступления в авансах и курс даты счёта: `payment_allocation` + `fx_rate` | |
| `vat_on_top` *(из практики)* | Цену согласовали с НДС, покупатель её оплатил, а в счёте НДС 16 % начислен сверху: в дебиторке висит лишний НДС | Счета с НДС «в т.ч.», товары и услуги без НДС, экспорт без НДС |
| `uncollected_service` *(из практики)* | Счёт просрочен и не оплачен ни на тенге, а клиенту уже продлили ту же подписку новым счётом | Открытый долг без продления, продление после оплаты, частично оплаченные счета |

Каждый тип настраивается независимо (`config.errors`, по 0–6 штук), взаимодействия — через `config.interactions`, ловушки — через `config.distractors`. Два типа из практики по умолчанию выключены, поэтому обязательный контракт кейса они не меняют. Оценщик, независимый аудитор, модель и тесты поддерживают их наравне с основными.

## Уровни сложности

`config.difficulty` задаёт, насколько плотно в книгах стоят законные «двойники» ошибок. Размер книги задаётся отдельно (`acts`, `filler`); в наборе `configs/curriculum.v2.json` уровни сочетают и то и другое.

| Уровень | Что меняется | Книга в наборе curriculum |
|---|---|---|
| `easy` | Ловушек вдвое меньше; время платежей в часовом поясе компании | ~25 счетов, ~230 строк |
| `medium` | Как в основных наборах (по умолчанию) | ~50 счетов, ~420 строк |
| `hard` | Ловушек вдвое больше. Время платежей в 6 разных смещениях. Добавляются 4 новых «двойника»: клиент оплатил счёт дважды; продление подписки после срока, но с оплатой вовремя; клиент оплатил цену без НДС; одна оплата за два счёта со ссылкой только на один | ~75 счетов, ~1 900 строк |

Измерено на 90 закрытых эпизодах (`python -m audit_env benchmark --curriculum --repeats 5`):

| Политика | easy: F1 / награда | medium: F1 / награда | hard: F1 / награда | Ложных на эпизод (easy → hard) |
|---|---|---|---|---|
| expert и **micro** | 1.000 / +0.980 | 1.000 / +0.968 | 1.000 / +0.916 | 0 → 0 |
| reconcile (простая сверка) | 0.204 / −0.602 | 0.114 / −0.787 | 0.075 / −0.891 | 5.5 → 21.8 |
| random | 0.167 / −0.671 | 0.167 / −0.671 | 0.167 / −0.671 | 0 |

Чем выше уровень, тем сильнее проваливаются эвристики: простая сверка тонет в ложных срабатываниях. Аудитор по правилам и повторяющий его `micro` остаются точными, то есть задача становится сложнее, но не неразрешимой. На `hard` награда ниже только из-за стоимости шагов: чтобы прочитать книгу в ~1 900 строк, нужно 43 шага вместо 11. Это и есть давление «экономии шагов» из кейса (подробнее — в разделе [Экономия шагов](#экономия-шагов)).

## Протокол жюри одной командой

`python -m audit_env jury` повторяет раздел 06 ТЗ: 20 закрытых эпизодов шаблона `configs/holdout-template.v2.json` (5 чистых, 5 со взаимодействиями, 4 с одной ошибкой, 6 со смесью), четыре политики организаторов и 20 парных проверок, в которых меняются порядок строк и все ID. Ключ выводится из `--seed`, поэтому таблица воспроизводится; `--report` пишет JSON.

| Политика | Ложных выводов на чистый эпизод | P / R / F1 на эпизодах с ошибками | Возврат, 95 % интервал | Норм. счёт | Шагов |
|---|---|---|---|---|---|
| oracle (только оценщик) | 0 | 1.000 / 1.000 / 1.000 | +0.980 [+0.970, +0.987] | 1.00 | 11.2 |
| reconcile (простая сверка) | 9.2 | 0.173 / 0.644 / 0.268 | −0.621 [−0.751, −0.491] | −0.08 | 16.2 |
| random (12 случайных страниц, ответ пустой) | 0 | 0 / 0 / 0 | −0.506 [−0.802, −0.111] | −0.00 | 13.0 |
| flag-all (атака «пометить всё») | 30 | 0.002 / 0.006 / 0.003 | −0.997 [−1.000, −0.992] | −0.34 | 16.2 |

**Пол:** политика, которая ничего не читает и сразу отправляет пустой ответ, получает на этом шаблоне −0.500 (+1 на 5 чистых эпизодах, −1 на 15 с ошибками). Нормированный счёт = (возврат − пол) / (oracle − пол): ни простая сверка, ни случайное чтение не поднимаются выше пола, а «пометить всё» опускается ниже. Интервалы — 95 % бутстреп по эпизодам (2 000 выборок, фиксированный seed).

Парные проверки: 20 из 20. В `verify` парная проверка сравнивает не только oracle (он повторяет эталон), но и независимого аудитора `expert`: его TP/FP/FN после перестановки и смены ID не меняются. Ключ таблицы выводится из `--seed` (`keys.table_key`), поэтому эпизоды воспроизводимы, но не секретны; для настоящей закрытой проверки — `jury --fresh-key`.

## Прогон LLM (диагностика)

Чтобы проверить, что задача не решается «в лоб», настоящие LLM прошли закрытые эпизоды через MCP-сервер теми же пятью инструментами и с тем же лимитом 100 шагов:

```bash
python -m audit_env llm-probe --provider openai --model <модель> --base-url <OpenAI-совместимый URL> \
  --episodes 5 --same-episodes --report <файл.json>
```

`--same-episodes` выводит ключ из `--seed`, поэтому все модели видят одни и те же эпизоды шаблона жюри: чистый (`holdout-01`), один тип ошибки (`holdout-11` — дубли, `holdout-13` — курс), смесь (`holdout-17`) и взаимодействия (`holdout-06`). Отчёты лежат в [docs/llm_probe/](docs/llm_probe/).

| Модель | Эпизодов | Ошибок найдено | Ложных выводов | F1 | Награда | Шагов |
|---|---|---|---|---|---|---|
| `deepseek-flash` (DeepSeek-V4.1-Flash), текущая политика | 5 | 11 из 13 | 2 | 0.87 | +0.69 | 23 |
| `deepseek-flash`, политика до уточнения правил | 5 | 9 из 13 | 2 | 0.82 | +0.54 | 48 |
| `gemini-3.5-flash-lite` | 5 | 0 из 13 | 0 | 0.20 | −0.60 | 10.6 |
| `gemini-3.5-flash` | 1 (чистый) | — | 0 | 1.00 | +0.98 | 10 |
| `nemotron-3.5-lightning` | 1 (чистый) | — | 7 | 0.00 | −1.00 | 6 |
| для сравнения: `expert` (правила `checks.py`) | 5 | 13 из 13 | 0 | 1.00 | +0.98 | 13.2 |

Что видно:
- сильная модель (`deepseek-flash`) решает задачу частично: чистую компанию оставляет без обвинений, дубли и смесь ошибок находит полностью, в эпизоде с ошибками курса пропускает одну из трёх, а в эпизоде со взаимодействующими ошибками (частичная валютная оплата на границе периода и т. п.) находит одну из четырёх и делает два ложных вывода (награда −0.62). Взаимодействия — самое трудное место, как и задумано в ТЗ. Полное чтение и сверка стоили ей в среднем 48 шагов из 100;
- лёгкая модель верно оставляет чистую компанию без обвинений, но на книгах с ошибками отправляет пустой ответ, часто прочитав 3–7 страниц, тогда как полное чтение этих книг — 10–15 шагов;
- быстрая модель на чистой компании, прочитав одну страницу книги, выдвинула 7 обвинений — оценщик засчитал все как ложные (−1);
- сильная модель прошла только чистый эпизод: бесплатная дневная квота закончилась.

Повторный прогон `deepseek-flash` на том же эпизоде со взаимодействиями дал 3 из 4 и ни одного ложного вывода: результат модели заметно меняется от запуска к запуску. Пропущенная ошибка — `fx_rate` у валютной оплаты на границе периода: модель верно увидела, что поступление проведено не в том периоде (`period_cutoff`), но не заметила, что его же пересчитали по курсу «наивной» даты. Нужный курс и строка проводки были ей показаны, то есть промах — в рассуждении, а не в данных: это и есть взаимодействие ошибок из ТЗ.

F1 в таблице — среднее по эпизодам (включая чистый, где F1 = 1); по всем 13 ошибкам вместе у `deepseek-flash` с текущей политикой P = 11/13, R = 11/13. После ревью судебного бухгалтера политика прямо называет правила, которые раньше были только в коде (что такое дубль; оплата на границе периода с неверным курсом — два вывода). С ней модель полностью решила эпизод со взаимодействиями (4 из 4 вместо 1 из 4) и тратила вдвое меньше шагов. Выборка — 5 эпизодов, результаты модели меняются от запуска к запуску, поэтому улучшение нельзя целиком приписать формулировкам.

Получается градиент, который и должна давать среда для обучения: лёгкие модели — около нуля, сильная LLM — большая часть ошибок с промахами на взаимодействиях, аудитор по правилам — всё. Задача решаема по доступным записям, требует полного чтения книги и сверки документов, а угадывание и недочитывание наказываются наградой. Это диагностика на пяти эпизодах, а не оценка моделей: выборка мала, у Gemini Flash всего один эпизод (кончилась бесплатная квота); прогон `deepseek-flash` стоил около $0.18.

## Экономия шагов

Шаг стоит 0.002 награды. Строки таблиц лежат в порядке непрозрачных ID, поэтому проводки любого документа могут оказаться на любой странице книги. Минимум для полного аудита — прочитать каждую страницу каждой нужной таблицы по одному разу (по 50 строк) и отправить ответ. Таблица курсов нужна, только если есть документы в валюте.

`python -m audit_env economy` проверяет на тех же 108 закрытых эпизодах три вещи.

1. **Эксперт и модель тратят ровно этот минимум:** в среднем 21 шаг, ни одного лишнего и ни одного пропущенного. Курсы они не читают, если все документы в тенге. Для своих папок (`audit`) это важно: там `fx.csv` обычно полный.
2. **Недочитывание не окупается.** Здесь агент применяет те же честные правила, но читает только часть книги:

   | Сколько книги прочитано | Чистые | С ошибками | Все эпизоды | TP | FP | FN | Шагов |
   |---|---|---|---|---|---|---|---|
   | вся книга | +0.965 | **+0.959** | **+0.960** | 360 | 0 | 0 | 21.0 |
   | без последней страницы | +0.722 | +0.826 | +0.803 | 326 | 11 | 34 | 20.0 |
   | 90 % | +0.723 | +0.767 | +0.757 | 309 | 17 | 51 | 19.4 |
   | 75 % | +0.808 | +0.371 | +0.469 | 230 | 41 | 130 | 17.3 |
   | 50 % | +0.813 | −0.047 | +0.144 | 139 | 43 | 221 | 14.2 |
   | только документы | +0.988 | −1.000 | −0.558 | 0 | 33 | 360 | 7.8 |

   Одна непрочитанная страница экономит 0.002 награды, а теряет в среднем 0.16. Пропадают доказательства, и появляются ложные выводы, даже на чистых книгах: если не видна строка оплаты, счёт выглядит неоплаченным, а поступление — ушедшим в аванс. Стоимость шага различает только ответы равной точности и не подталкивает агента недочитывать.
3. **Самые большие допустимые книги** (около 1 940 строк книги, 89 счетов, 72 оплаты, курсы двух валют) читаются целиком за 48 шагов из 100, так что полный аудит всегда помещается в лимит.

## Обучение модели

`python -m audit_env train` работает только на CPU и занимает около 10 секунд:
1. генерирует 120 train-эпизодов всех трёх уровней сложности, половина из них с ошибками из практики;
2. обучает логистическую модель для каждого из 6 типов на признаках из публичных записей;
3. подбирает порог отправки по средней терминальной награде среды на отдельной валидационной выборке (на текущих данных пороги 0.4–0.9 дают одинаковую награду, выбран 0.5);
4. сравнивает результат с простой сверкой, экспертом и oracle на отложенных dev, обоих закрытых шаблонах и уровнях сложности.

Модель и отчёт лежат в `models/`. Сравнение с простой сверкой, экспертом и oracle сделано только на отложенных seed и конфигурациях с отдельным ключом; это свежие эпизоды того же генератора, а не другое распределение. Превосходства над аудитором по правилам `micro` не показывает и не заявляет: он использует его вспомогательные функции и признаки-индикаторы правил. Подробности — в [docs/micro-model.md](docs/micro-model.md).

## Для команды UI

`python -m audit_env serve` поднимает на `http://127.0.0.1:8765/` веб-интерфейс в стиле Excel (лента, листы-вкладки, таблицы с сеткой) и HTTP/JSON API, без внешних зависимостей и без сети: страница, скрипт и стили лежат в `audit_env/ui/`, политика безопасности (CSP) запрещает загрузку чего-либо со стороны. В интерфейсе можно создать эпизод (seed, сложность, режим, набор ошибок), посмотреть документы, книгу, курсы и учётную политику, запустить любую базовую политику и перейти от каждого доказательства к строке или документу, а также пройти аудит вручную теми же пятью инструментами и с тем же лимитом шагов. В открытом режиме после отправки видны P, R, F1 и награда, в закрытом оценка остаётся у оценщика. UI баллов по ТЗ не даёт и нужен для демонстрации. Через API можно:
- создать эпизод или импортировать папку с документами;
- делать шаги;
- запустить агента (`expert`, `micro`, `reconcile`, …);
- получить аудит папки.

Эталон через API не отдаётся никогда. Описание и примеры — в [docs/api.md](docs/api.md).

## Откуда взяты параметры генератора

Все компании, люди, счета, документы и суммы в репозитории и в эпизодах вымышлены и создаются генератором. Диапазоны цен (абонплаты 5 000–48 000 ₸, внедрение 60 000–150 000 ₸), НДС 16 % «в т.ч.» с округлением по строке, акты, выписанные в следующем месяце за услуги прошлого, и типовые ситуации (повторяющиеся абонплаты, переплата с уходом излишка в аванс, предоплата, два счёта одному клиенту от разных менеджеров) подобраны по практике учёта небольшой сервисной компании в Казахстане. Оттуда же два дополнительных типа ошибок: `vat_on_top` (НДС начислили сверху цены) и `uncollected_service` (подписку продлили, не получив оплату).

Реальные документы, реквизиты, выписки и результаты их обработки в репозиторий и в сдачу не входят и для проверки не нужны. Тест `tests/test_episode_io_hygiene.py` проверяет, что в файлах нет счетов, БИН и выгрузок банка.

## Честные ограничения

Границы модели — так задумано:
- Эпизод — одна компания и один месяц, как определено в ТЗ. Книга ведётся в KZT, валютные суммы есть только в документах: так ведёт учёт казахстанская компания.
- Ошибки — это неверные решения при проводке и выставлении документов. Документы, которые вовсе не попали в учёт, и партионный учёт склада не моделируются: ТЗ их не требует. Себестоимость задана для каждой строки накладной.
- `uncollected_service` и платные продления-«двойники» строятся на подписках (`SUB`, `SUP`), а валютные ошибки — на услугах иностранным клиентам: товары за валюту генератор не продаёт и в чистых книгах.

Что проверено, а что нет:
- Эксперт `checks.py` и повторяющий его `micro` решают все эпизоды. Это доказывает решаемость и корректность эталона, но не сложность задачи. Сложность показывают провал простой сверки (F1 0.20 → 0.08 от easy к hard) и прогон настоящих LLM (`deepseek-flash` — 9 ошибок из 13 в первом прогоне, лёгкая модель — ни одной; n = 5, разброс между запусками заметный) в разделе [Прогон LLM](#прогон-llm-диагностика); последний — диагностика на нескольких эпизодах, а не оценка модели.
- Параметры генератора подобраны вручную по практике одной сервисной компании; репрезентативность для других компаний не проверялась.
- Контроль утечек (раздел 10 `verify`) проверяет конкретный список: ID, порядок строк, секунды меток времени, «это накладная», «на счёт есть оплата», срок оплаты и число счетов у клиента. Секунды меток когда-то были приметой (`:00` у пограничных платежей), четыре структурные приметы давали AUROC 0.11–0.29; все устранены в генераторе. Приметы вне этого списка не исключены.
- Известная неустранённая примета: цели ошибок с оплатой внутри периода генерируются с окончанием услуги не позже чем за 7 дней до конца месяца, а у `uncollected_service` — в первую неделю. Поэтому признак «дней от окончания услуги до конца периода» отделяет ошибочные счета от обычных с AUROC около 0.66 (нашёл Neon при последней проверке, мы измерили на 360 закрытых эпизодах). Исправление готово в виде черновика: распределить окончание услуги целей по всему месяцу, оставив 3 дня запаса только тем, кому нужна оплата в периоде (AUROC падает до 0.53–0.58). Оно меняет все открытые эпизоды и примеры каталога ошибок, поэтому в сдачу не вошло. В раздел 10 `verify` этот признак пока не добавлен.
- Граница изоляции стороннего агента — контейнер (`demo --agent-image`, `make docker-agent`). Процесс того же пользователя может прочитать память и исходное окружение оценщика через `/proc` (это показал наш red team), поэтому закрытый эпизод отказывается запускать недоверенного агента подпроцессом (`runner.run_subprocess` без `trusted=True`); подпроцессом идут только наши политики и клиент docker. Ключ агенту не передаётся ни через окружение, ни через файл, а по умолчанию живёт только в памяти оценщика.
- Независимый аудитор `checks.py`, оценщик и генератор написаны одной командой по одной `policy.json`. Проверка эталона ловит ошибки реализации, но не ошибочное прочтение правила всеми тремя сразу; для этого мы сверяли формулы вручную (судебный бухгалтер на открытых эпизодах) и уточнили формулировки политики.
- Правила, о которых стоит знать: в доказательствах нельзя ссылаться на посторонние ID, даже увиденные (защита от «раздувания доказательств», атака `evidence-padding`); `inspection_steps` при отправке не считает сам шаг отправки, а при обрыве по лимиту равно 100; обрыв по лимиту на чистой книге даёт +0.8, как пустой ответ по формуле ТЗ (атака `stall` поэтому уступает молчанию, но выше нуля).
- Политика `random` — случайный исследователь из ТЗ: читает 12 случайных страниц и отправляет пустой ответ. Её F1 на чистых эпизодах равен 1, поэтому в таблице жюри P/R/F1 показаны отдельно по эпизодам с ошибками.
- Контракт `reset`/`step` повторяет Gymnasium. Адаптер `audit_env/gym_adapter.py` наследует `gymnasium.Env`, если пакет установлен; в режиме `json_text=True` он проходит `gymnasium.utils.env_checker.check_env` (gymnasium 1.x). Пространства текстовые (JSON): тензорной политике нужен свой кодировщик. В закрытом режиме терминальная награда равна `None`.
