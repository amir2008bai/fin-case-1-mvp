# Финансовый кейс 1: RL-среда для ИИ-аудитора

Воспроизводимый симулятор для обучения и проверки ИИ-аудитора. В нём есть:
- синтетическая компания за отчётный период: продаёт услуги (акты) и товары (накладные), ведёт книгу проводок, получает оплаты от клиентов из трёх стран; всё в форматах кейса;
- инструменты расследования в стиле Gymnasium (`reset`/`step`);
- скрытые ошибки: 4 обязательных типа из кейса, 2 сценария их взаимодействия и 2 дополнительных типа из реальной практики, у каждой ошибки записана причина;
- независимая проверка эталона;
- общий matcher и награда `clip(2·F1 − 1 − 0.002·steps, −1, 1)`;
- обученная на CPU модель, которая на закрытых проверках находит все ошибки без ложных срабатываний;
- red team: 12 нечестных стратегий и перебор seed не обходят ни честную работу, ни молчание.

## Проверка одной командой

Нужен Python 3.11+. Внешние пакеты, сеть, GPU и платные API не нужны.

```bash
python -m audit_env verify
```

Команда последовательно:
1. прогоняет все тесты;
2. печатает 22 именованные проверки контракта, изоляции, награды и воспроизводимости;
3. доказывает корректность эталона на 60 случайных конфигурациях со свежим секретным ключом;
4. сверяет закоммиченные `data/` с регенерацией байт в байт;
5. гоняет 4 базовые политики и эксперта на шаблоне закрытой проверки (20 конфигураций, 5 чистых и 5 со взаимодействием, случайные seed), включая парные проверки со сменой ID и порядка;
6. делает то же на расширенном шаблоне: ошибки из практики и разные доли товаров;
7. делает то же на трёх уровнях сложности (easy → medium → hard, книги до ~2000 строк);
8. атакует оценщика 12 нечестными агентами и перебором seed ([Атаки на оценщика](#атаки-на-оценщика)) и падает, если хоть одна атака обходит честную работу или молчание.

Отчёт пишется в `build/verify-report.json`, при любом сбое код выхода ненулевой. Время около 50 секунд.

### Контейнер (офлайн, 2 CPU, 4 ГБ, только чтение)

```bash
docker build --target verify -t fintech-audit:verify .
docker run --rm --pull=never --network=none --read-only --cap-drop=ALL --cpus=2 --memory=4g \
  --tmpfs /tmp:rw,size=256m fintech-audit:verify
```

То же самое делает `make docker-verify`. Базовый образ `python:3.11.14-slim` закреплён по digest.

Агент в отдельном контейнере: образ без генератора, без оценщика и без ответов, запуск `--network=none --read-only`. Оценщик остаётся снаружи и общается с агентом по JSONL.

```bash
docker build --target agent -t fintech-audit:agent .
python -m audit_env demo --closed --policy expert --agent-image fintech-audit:agent
```

`make docker-agent` прогоняет так агентов `expert` и `micro`. CI (`.github/workflows/verify.yml`) запускает `verify` на Python 3.11 в Linux и Windows, затем `docker-verify` и `docker-agent`.

## Что внутри эпизода

Эпизод — одна компания и один месяц, 200–2000 строк книги, 20–200 документов, 0–12 ошибок. Книга ведётся в KZT, есть клиенты из Кыргызстана (USD) и России (RUB).

Компания продаёт:
- **услуги** — подписки на ПО, сопровождение, внедрение, обучение; документ — акт выполненных работ (форма Р-1), для экспорта услуг — акт без НДС;
- **товары** — онлайн-ККМ, POS-терминалы, сканеры, принтеры, термолента; документ — накладная на отпуск запасов (форма З-2).

Доля товаров задаётся `config.goods_percent`; по умолчанию накладных примерно столько же, сколько актов. Учёт товаров:
- при отгрузке выручка и НДС проводятся так же, как по услугам, а себестоимость списывается со склада: Дт 7010 Кт 1330;
- закупки у поставщика: Дт 1330 и Дт 1420 (НДС к возмещению), Кт 3310;
- на начало периода есть остаток склада.

НДС 16 % включён в цену, к каждому документу с НДС выписан ЭСФ.

| Файл | Содержимое |
|---|---|
| `manifest.json` | `schema_version`, `episode_id`, `base_currency`, `period_start`/`period_end`, `timezone`, число записей и документов, разрядность валют, правила округления |
| `ledger.csv` | `row_id,timestamp,account,debit_minor,credit_minor,currency,entity_id,invoice_id,payment_id`. Отсутствующая связь записывается как `null` |
| `invoices.jsonl` | `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items`. В строках есть период услуги и НДС |
| `payments.jsonl` | `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs`. Если плательщик не указал счёт, `invoice_refs = null` |
| `fx.csv` | `fx_id, date, source_currency, target_currency, rate`. Курс — десятичная строка; `fx_id` добавлен, чтобы курс можно было цитировать |
| `policy.json` | Все правила: границы периода, признание выручки, пересчёт валют, распределение платежей, НДС, правила выводов и доказательств |

Закрытые файлы оценщика: `truth.json` (тип, затронутые ID, сумма, валюта, допуск, допустимые наборы доказательств) и `provenance.json` (seed, конфигурация, отпечаток ключа, хэш чистой книги, причинные изменения «до/после»). Агент их не видит.

## Ошибки и ловушки

| Тип | Что ломается | Законные «двойники», которые не являются ошибкой |
|---|---|---|
| `duplicate_invoice` | Второй счёт на ту же услугу, клиента и период проведён в выручку (два менеджера выставили два счёта) | Та же абонплата в другом периоде, одинаковые цены у разных клиентов, многострочные счета |
| `payment_allocation` | Поступление по открытому счёту целиком или частично ушло в авансы 3510 вместо погашения 1210 | Предоплата до окончания услуги, переплата «с лишним нулём», оплата без ссылки на счёт, зачёт входящих авансов, разбитые и сводные оплаты |
| `fx_rate` | Счёт или поступление пересчитаны по курсу не той даты или по опечатанному курсу | Обычные курсовые разницы 6250/7430 на каждом валютном поступлении |
| `period_cutoff` | Выручка по услуге прошлого или следующего периода признана в этом; поступление после конца периода проведено в нём по дате в часовом поясе плательщика | Счета, выписанные позже за прошлый период; счета, выписанные после конца периода; метки времени, у которых дата «на стене» вне периода, а момент внутри |
| IX-A `fx_boundary_payment` | Частичная валютная оплата на границе периода: `period_cutoff` + `fx_rate` | |
| IX-B `fx_partial_allocation` | Часть валютного поступления в авансах и курс даты счёта: `payment_allocation` + `fx_rate` | |
| `vat_on_top` *(из практики)* | Цену согласовали с НДС, покупатель её оплатил, а в счёте НДС 16 % начислен сверху: в дебиторке висит лишний НДС | Счета с НДС «в т.ч.», товары и услуги без НДС, экспорт без НДС |
| `uncollected_service` *(из практики)* | Счёт просрочен и не оплачен ни на тенге, а клиенту уже продлили ту же подписку новым счётом | Открытый долг без продления, продление после оплаты, частично оплаченные счета |

Каждый тип настраивается независимо (`config.errors`, по 0–6 штук), взаимодействия — через `config.interactions`, ловушки — через `config.distractors`. Два типа из практики по умолчанию выключены, поэтому обязательный контракт кейса они не меняют. Оценщик, независимый аудитор, модель и тесты поддерживают их наравне с основными.

## Уровни сложности

`config.difficulty` задаёт, насколько плотно в книгах стоят законные «двойники» ошибок. Размер книги задаётся отдельно (`acts`, `filler`); в наборе `configs/curriculum.v2.json` уровни сочетают и то и другое.

| Уровень | Что меняется | Книга в наборе curriculum |
|---|---|---|
| `easy` | Ловушек вдвое меньше; время платежей в часовом поясе компании | ~25 счетов, ~230 строк |
| `medium` | Как в основных наборах (по умолчанию) | ~50 счетов, ~420 строк |
| `hard` | Ловушек вдвое больше. Время платежей в 6 разных смещениях. Добавляются 4 новых «двойника»: клиент оплатил счёт дважды; продление подписки после срока, но с оплатой вовремя; клиент оплатил цену без НДС; одна оплата за два счёта со ссылкой только на один | ~75 счетов, ~1 900 строк |

Измерено на 90 закрытых эпизодах (`python -m audit_env benchmark --curriculum`):

| Политика | easy: F1 / награда | medium: F1 / награда | hard: F1 / награда | Ложных на эпизод (easy → hard) |
|---|---|---|---|---|
| expert и **micro** | 1.000 / +0.980 | 1.000 / +0.970 | 1.000 / +0.916 | 0 → 0 |
| reconcile (простая сверка) | 0.181 / −0.647 | 0.121 / −0.772 | 0.069 / −0.901 | 5.4 → 21.9 |
| random | 0.167 / −0.671 | 0.167 / −0.671 | 0.167 / −0.671 | 0 |

Чем выше уровень, тем сильнее проваливаются эвристики: простая сверка тонет в ложных срабатываниях. Аудитор по правилам и модель остаются точными, то есть задача становится сложнее, но не неразрешимой. На `hard` награда ниже только из-за стоимости шагов: чтобы прочитать книгу в ~1 900 строк, нужно 43 шага вместо 11. Это и есть давление «экономии шагов» из кейса.

## Результаты (закрытый режим, свежие seed и секретный ключ)

Шаблон жюри: 100 эпизодов (20 конфигураций × 5 seed), 340 ошибок. Средняя награда:

| Политика | Чистые | Одна ошибка | Смесь | Взаимодействия | Шагов | мс/эпизод |
|---|---|---|---|---|---|---|
| oracle (только оценщик) | +1.000 | +0.980 | +0.962 | +0.981 | 11 | <1 |
| expert (правила `checks.py`) | +0.973 | +0.972 | +0.968 | +0.969 | 16 | 6 |
| **micro (обученная модель)** | **+0.973** | **+0.972** | **+0.968** | **+0.969** | 16 | 6 |
| reconcile (простая сверка) | −1.000 | −0.541 | −0.414 | −0.641 | 16 | 5 |
| random | +0.976 | −1.000 | −1.000 | −1.000 | 13 | 2 |
| flag-all (атака) | −1.000 | −1.000 | −0.997 | −1.000 | 16 | 5 |

Расширенный шаблон (`configs/holdout-extended.v2.json`): 100 эпизодов, 380 ошибок, включая 100 `vat_on_top` и 90 `uncollected_service`.

| Политика | Чистые | Только ошибки из практики | Смесь всех 6 типов |
|---|---|---|---|
| expert | +0.971 | +0.972 | +0.964 |
| **micro** | **+0.971** | **+0.972** | **+0.964** |
| reconcile | −1.000 | −1.000 | −0.595 |
| flag-all | −1.000 | −1.000 | −0.998 |

Обученная модель нашла все 930 ошибок трёх закрытых наборов (шаблон жюри, расширенный и уровни сложности) без единого ложного срабатывания. Простая сверка не находит ни одной ошибки из практики и проигрывает молчанию на чистых книгах. Почему, разобрано в [docs/failure_analysis.md](docs/failure_analysis.md).

Высокая награда oracle и эксперта сама по себе не доказывает сложность задачи. Это проверка того, что задача решаема по доступным записям.

## Атаки на оценщика

`python -m audit_env attacks` выставляет против оценщика 12 нечестных агентов в закрытом режиме. Прогон идёт на 108 эпизодах: шаблон жюри, расширенный шаблон и уровень `hard`, по 3 seed на конфигурацию. Из них 24 чистых, ошибок 360. Секретный ключ выводится из `--seed`, поэтому таблица воспроизводится байт в байт; с флагом `--fresh-key` ключ берётся случайный. Средняя награда:

| Агент | Что пробует | Чистые | С ошибками | TP | FP |
|---|---|---|---|---|---|
| honest (эталон) | честный аудитор по правилам (`expert`) | +0.965 | **+0.959** | 360 | 0 |
| silence (эталон) | сразу пустой ответ | **+1.000** | −1.000 | 0 | 0 |
| flag-all | каждый документ со всеми его строками | −1.000 | −1.000 | 0 | 3 240 |
| shortcut | структурные приметы вместо анализа | −1.000 | −1.000 | 0 | 3 212 |
| type-hedge | каждую честную находку под всеми 6 типами | +0.965 | −0.480 | 300 | 1 500 |
| amount-hedge | каждую честную находку с тремя суммами | +0.965 | −0.043 | 354 | 708 |
| repeat-farming | каждую честную находку дважды | +0.965 | +0.292 | 360 | 360 |
| noise-plus-honest | честные находки и 5 догадок сверху | −1.000 | +0.150 | 360 | 540 |
| evidence-stuffing | верные тип и сумма, чужие доказательства | +0.965 | −1.000 | 0 | 360 |
| evidence-padding | честные доказательства и посторонние строки | +0.965 | −1.000 | 0 | 360 |
| id-guess | ID, которых агент не видел | −1.000 | −1.000 | 0 | 1 080 |
| persuasion | выдуманные обвинения с «убедительным» объяснением | −1.000 | −1.000 | 0 | 540 |
| persuasion-plain | те же обвинения без текста (контроль) | −1.000 | −1.000 | 0 | 540 |
| stall | тянуть до лимита шагов и не отвечать | +0.800 | −1.000 | 0 | 0 |

На каждом эпизоде проверяются три инварианта (раздел 8 `verify`, `tests/test_attacks.py`):
- на чистых книгах любое обвинение хуже молчания, и ни одна атака не набирает больше молчания;
- на книгах с ошибками ни одна атака не набирает больше честного аудитора;
- текст объяснения не влияет на оценку: `persuasion` и `persuasion-plain` получают одинаковую награду в каждом эпизоде.

Отдельная атака — перебор seed. Атакующий знает код и конфигурацию и перебирает 200 000 seed. На опубликованном ключе он восстанавливает seed эпизода (это контроль, что атака работает), на секретном — нет. Значит, эталон закрытого набора нельзя пересчитать по `episode_id`. Почему проваливается каждая атака, разобрано в [docs/failure_analysis.md](docs/failure_analysis.md#нечестные-стратегии-red-team).

## Команды

```bash
python -m audit_env verify                    # единая проверка
python -m audit_env demo --policy expert      # один эпизод, метрики
python -m audit_env benchmark --holdout       # таблица по категориям (шаблон жюри)
python -m audit_env benchmark --extended      # то же для ошибок из практики и товаров
python -m audit_env benchmark --curriculum    # easy / medium / hard
python -m audit_env failures [--extended | --curriculum]   # измеренный разбор сбоев по причинам
python -m audit_env attacks                   # red team: 12 нечестных агентов и перебор seed против оценщика
python -m audit_env dataset data              # экспорт 10 train + 10 dev, ответов, траекторий, SHA256SUMS
python -m audit_env selfcheck --n 300         # доказательство корректности эталона на N конфигурациях
python -m audit_env train                     # обучить микромодель и сравнить на отложенных данных
python -m audit_env audit <папка>             # проверить свои документы (6 файлов) без эталона
python -m audit_env audit-truth <папка> <ответы>   # независимо перепроверить эталон папки
python -m audit_env serve                     # локальный API для UI: http://127.0.0.1:8765
```

## Открытые данные

- `data/episodes/{train,dev}/<episode_id>/` — 10 train и 10 dev эпизодов (шесть файлов кейса и `documents.jsonl`).
- `data/answers/...` — их `truth.json` и `provenance.json`.
- `data/trajectories.jsonl` — траектории эксперта в открытом режиме, поля: `episode_id, step, action, observation, reward, terminated, truncated`; закрытого эталона в наблюдениях нет.
- `data/trajectories/{oracle,reconcile,random,flag-all}.jsonl` — траектории четырёх базовых политик.
- `data/benchmark.json`, `data/index.json`, `data/SHA256SUMS`.

Конфигурации версионированы:
- `configs/suite.v2.json` — открытые train/dev с seed; в эпизодах со смесью ошибок есть и типы из практики;
- `configs/holdout-template.v2.json` — 20 конфигураций без seed, seed и ключ подставляет проверяющий;
- `configs/holdout-extended.v2.json` — 10 конфигураций с ошибками из практики и товарами;
- `configs/curriculum.v2.json` — по 6 конфигураций на уровни easy, medium и hard.

## Обучение модели

`python -m audit_env train` работает только на CPU и занимает около 16 секунд:
1. генерирует 120 train-эпизодов всех трёх уровней сложности, половина из них с ошибками из практики;
2. обучает логистическую модель для каждого из 6 типов на признаках из публичных записей;
3. подбирает порог по средней терминальной награде среды;
4. сравнивает результат с простой сверкой, экспертом и oracle на отложенных dev, обоих закрытых шаблонах и уровнях сложности.

Модель и отчёт лежат в `models/`. Улучшение заявляется только по отложенным данным. Подробности — в [docs/micro-model.md](docs/micro-model.md).

## Для команды UI

`python -m audit_env serve` поднимает HTTP/JSON на `127.0.0.1` без внешних зависимостей. Через него можно:
- создать эпизод или импортировать папку с документами;
- делать шаги;
- запустить агента (`expert`, `micro`, `reconcile`, …);
- получить аудит папки.

Эталон через API не отдаётся никогда. Описание и примеры — в [docs/api.md](docs/api.md).

## Реальные документы

Генератор синтетических эпизодов построен по агрегированной статистике реального документооборота ТОО «ГК Эксперт» (резидент Astana Hub) за I квартал 2026 года: банковская выписка и электронные акты выполненных работ, использованы с согласия компании. По ним подобраны:
- типовые суммы услуг (абонплаты 5 000–48 000 ₸, внедрение 60 000–150 000 ₸);
- НДС 16 % «в т.ч.» с округлением по строке;
- акты, выписанные в следующем месяце за услуги прошлого;
- типичные ситуации: повторяющиеся абонплаты, переплата с уходом излишка в аванс, предоплата, два счёта одному клиенту от разных менеджеров.

Кроме того, аудиторы прогнаны локально на этом квартале в режиме без эталона. В марте они нашли 6 кандидатов на ошибку периода (акты, выписанные в марте за работы января–февраля); правила и обученная модель дали один и тот же набор. Это гипотезы, полученные в предположении, что выручка проводится датой акта; с учётом компании их не сверяли. Подробности и ограничения — в [разборе сбоев](docs/failure_analysis.md#реальный-квартал-тоо-гк-эксперт-только-агрегаты).

Две ошибки из практики, `vat_on_top` и `uncollected_service`, тоже взяты из этого документооборота: так ошибались на практике (НДС начисляли сверху цены после перехода на НДС; подписку продлевали по просьбе клиента, а оплату так и не получали).

Сами документы, реквизиты и любые реальные данные в репозиторий и сдачу не входят. Все эпизоды среды синтетические, а тест `tests/test_episode_io_hygiene.py` проверяет, что в репозитории нет счетов, БИН и выгрузок банка.

## Честные ограничения

- Одна компания и один месяц на эпизод. Книга ведётся только в KZT, валютные суммы есть только в документах.
- Ошибки — это неверные решения при проводке или выставлении документов. Документы, которые вовсе не попали в учёт, не моделируются. Себестоимость товаров задана для каждой строки, движение склада по партиям не ведётся.
- Эксперт `checks.py` и обученная модель решают все эпизоды. Это доказательство решаемости и корректности эталона, а не оценка сложности для большой языковой модели, которой придётся рассуждать по тем же правилам.
- Калибровка взята по одному кварталу одной компании.
- `AuditEnv` повторяет контракт Gymnasium, но не наследует `gymnasium.Env`; в закрытом режиме терминальная награда равна `None`.
- Модули прототипа (`llm*`, `hf_*`, `rag*`, `tests_extras/`) пока написаны под первую предметную модель и в `verify` не входят.
