# Финансовый кейс 1: RL-среда для ИИ-аудитора

Воспроизводимый симулятор для обучения и проверки ИИ-аудитора. В нём есть:
- синтетическая компания за отчётный период: книга проводок, счета, банковские поступления и курсы валют в форматах кейса;
- инструменты расследования в стиле Gymnasium (`reset`/`step`);
- скрытые ошибки четырёх типов с записанной причиной;
- независимая проверка эталона;
- общий matcher и награда `clip(2·F1 − 1 − 0.002·steps, −1, 1)`.

## Проверка одной командой

Нужен Python 3.11+. Внешние пакеты, сеть, GPU и платные API не нужны.

```bash
python -m audit_env verify
```

Команда последовательно:
1. прогоняет все тесты;
2. печатает 22 именованные проверки контракта, изоляции, награды и воспроизводимости;
3. доказывает корректность эталона на 60 случайных конфигурациях со свежим секретным ключом;
4. сверяет закоммиченные `data/` с регенерацией байт в байт;
5. гоняет 4 базовые политики и эксперта на шаблоне закрытой проверки (20 конфигураций, 5 чистых и 5 со взаимодействием, случайные seed), включая парные проверки со сменой ID и порядка.

Отчёт пишется в `build/verify-report.json`, при любом сбое код выхода ненулевой. Время около 20 секунд.

### Контейнер (офлайн, 2 CPU, 4 ГБ, только чтение)

```bash
docker build --target verify -t fintech-audit:verify .
docker run --rm --pull=never --network=none --read-only --cap-drop=ALL --cpus=2 --memory=4g \
  --tmpfs /tmp:rw,size=256m fintech-audit:verify
```

То же самое делает `make docker-verify`. Базовый образ `python:3.11.14-slim` закреплён по digest. CI (`.github/workflows/verify.yml`) запускает `verify` на Python 3.11 в Linux и Windows, а также в контейнере.

## Что внутри эпизода

Эпизод — одна компания и один месяц, 200–2000 строк книги, 20–200 документов, 0–12 ошибок. Компания оказывает услуги, книга ведётся в KZT, есть клиенты из Кыргызстана (USD) и России (RUB), НДС 16 % включён в цену.

| Файл | Содержимое |
|---|---|
| `manifest.json` | `schema_version`, `episode_id`, `base_currency`, `period_start`/`period_end`, `timezone`, число записей и документов, разрядность валют, правила округления |
| `ledger.csv` | `row_id,timestamp,account,debit_minor,credit_minor,currency,entity_id,invoice_id,payment_id`. Отсутствующая связь записывается как `null` |
| `invoices.jsonl` | `doc_id, invoice_id, entity_id, issued_at, due_at, currency, total_minor, line_items`. В строках есть период услуги и НДС |
| `payments.jsonl` | `doc_id, payment_id, timestamp, currency, amount_minor, invoice_refs`. Если плательщик не указал счёт, `invoice_refs = null` |
| `fx.csv` | `fx_id, date, source_currency, target_currency, rate`. Курс — десятичная строка; `fx_id` добавлен, чтобы курс можно было цитировать |
| `policy.json` | Все правила: границы периода, признание выручки, пересчёт валют, распределение платежей, НДС, правила выводов и доказательств |

Закрытые файлы оценщика: `truth.json` (тип, затронутые ID, сумма, валюта, допуск, допустимые наборы доказательств) и `provenance.json` (seed, конфигурация, отпечаток ключа, хэш чистой книги, причинные изменения «до/после»). Агент их не видит.

## Ошибки и ловушки

| Тип | Что ломается | Законные «двойники», которые не являются ошибкой |
|---|---|---|
| `duplicate_invoice` | Второй счёт на ту же услугу, клиента и период проведён в выручку (два менеджера выставили два счёта) | Та же абонплата в другом периоде, одинаковые цены у разных клиентов, многострочные счета |
| `payment_allocation` | Поступление по открытому счёту целиком или частично ушло в авансы 3510 вместо погашения 1210 | Предоплата до окончания услуги, переплата «с лишним нулём», оплата без ссылки на счёт, зачёт входящих авансов, разбитые и сводные оплаты |
| `fx_rate` | Счёт или поступление пересчитаны по курсу не той даты или по опечатанному курсу | Обычные курсовые разницы 6250/7430 на каждом валютном поступлении |
| `period_cutoff` | Выручка по услуге прошлого или следующего периода признана в этом; поступление после конца периода проведено в нём по дате в часовом поясе плательщика | Счета, выписанные позже за прошлый период; счета, выписанные после конца периода; метки времени, у которых дата «на стене» вне периода, а момент внутри |
| IX-A `fx_boundary_payment` | Частичная валютная оплата на границе периода: `period_cutoff` + `fx_rate` | |
| IX-B `fx_partial_allocation` | Часть валютного поступления в авансах и курс даты счёта: `payment_allocation` + `fx_rate` | |

Каждый тип настраивается независимо (`config.errors`, по 0–6 штук), взаимодействия — через `config.interactions`, ловушки — через `config.distractors`.

## Результаты (закрытый режим, свежие seed и секретный ключ)

100 эпизодов закрытого шаблона, средняя награда:

| Политика | Чистые | Одна ошибка | Смесь | Взаимодействия | Шагов | мс/эпизод |
|---|---|---|---|---|---|---|
| oracle (только оценщик) | +1.000 | F1 = 1 | F1 = 1 | F1 = 1 | 1–20 | <1 |
| expert (правила `checks.py`) | +0.976 | +0.975 | +0.972 | +0.973 | 14 | 5 |
| micro (обученная модель) | +0.897 | +0.975 | +0.960 | +0.973 | 14 | 5 |
| reconcile (простая сверка) | −1.000 | −0.571 | −0.440 | −0.629 | 14 | 5 |
| random | +0.976 | −1.000 | −1.000 | −1.000 | 13 | 2 |
| flag-all (атака) | −1.000 | −0.995 | −1.000 | −1.000 | 14 | 4 |

Почему простая сверка проваливается, разобрано в [docs/failure_analysis.md](docs/failure_analysis.md). Высокая награда oracle и эксперта сама по себе не доказывает сложность задачи. Это проверка того, что задача решаема по доступным записям.

## Команды

```bash
python -m audit_env verify                    # единая проверка
python -m audit_env demo --policy expert      # один эпизод, метрики
python -m audit_env benchmark --holdout       # таблица по категориям
python -m audit_env dataset data              # экспорт 10 train + 10 dev, ответов, траекторий, SHA256SUMS
python -m audit_env selfcheck --n 300         # доказательство корректности эталона на N конфигурациях
python -m audit_env train                     # обучить микромодель и сравнить на отложенных данных
python -m audit_env audit <папка>             # проверить свои документы (6 файлов) без эталона
python -m audit_env audit-truth <папка> <ответы>   # независимо перепроверить эталон папки
python -m audit_env serve                     # локальный API для UI: http://127.0.0.1:8765
```

## Открытые данные

- `data/episodes/{train,dev}/<episode_id>/` — 10 train и 10 dev эпизодов (шесть файлов кейса и `documents.jsonl`).
- `data/answers/...` — их `truth.json` и `provenance.json`.
- `data/trajectories.jsonl` — траектории эксперта в открытом режиме, поля: `episode_id, step, action, observation, reward, terminated, truncated`; закрытого эталона в наблюдениях нет.
- `data/trajectories/{oracle,reconcile,random,flag-all}.jsonl` — траектории четырёх базовых политик.
- `data/benchmark.json`, `data/index.json`, `data/SHA256SUMS`.

Конфигурации версионированы: `configs/suite.v2.json` (открытые train/dev с seed) и `configs/holdout-template.v2.json` (20 конфигураций без seed; seed и ключ подставляет проверяющий).

## Обучение модели

`python -m audit_env train` работает только на CPU и занимает около 12 секунд:
1. генерирует 120 train-эпизодов;
2. обучает по-типовые логистические модели на признаках из публичных записей;
3. подбирает порог по средней терминальной награде среды;
4. сравнивает результат с простой сверкой, экспертом и oracle на отложенных dev и закрытом шаблоне.

Модель и отчёт лежат в `models/`. Улучшение заявляется только по отложенным данным. Подробности — в [docs/micro-model.md](docs/micro-model.md).

## Для команды UI

`python -m audit_env serve` поднимает HTTP/JSON на `127.0.0.1` без внешних зависимостей. Через него можно:
- создать эпизод или импортировать папку с документами;
- делать шаги;
- запустить агента (`expert`, `micro`, `reconcile`, …);
- получить аудит папки.

Эталон через API не отдаётся никогда. Описание и примеры — в [docs/api.md](docs/api.md).

## Реальные документы

Генератор синтетических эпизодов откалиброван по агрегированной статистике реального документооборота ТОО «ГК Эксперт» (резидент Astana Hub) за I квартал 2026 года: банковская выписка и электронные акты выполненных работ, использованы с согласия компании. По ним взяты типовые суммы, доля оплат со ссылкой на счёт, лаги между датой услуги и датой акта, повторяющиеся абонплаты, переплаты и авансы. Сами документы, реквизиты и любые реальные данные в репозиторий и сдачу не входят. Все эпизоды среды синтетические, а тест `tests/test_episode_io_hygiene.py` проверяет, что в репозитории нет счетов, БИН и выгрузок банка.

## Честные ограничения

- Одна компания и один месяц на эпизод. Книга ведётся только в KZT, валютные суммы есть только в документах.
- Ошибки — это неверные решения при проводке. Документы, которые вовсе не попали в учёт, и ошибки в базе НДС (НДС «сверху» при оплате без НДС) не моделируются.
- Эксперт `checks.py` решает все эпизоды. Это доказательство решаемости и корректности эталона, а не оценка сложности для реальной модели.
- Калибровка взята по одному кварталу одной компании.
- `AuditEnv` повторяет контракт Gymnasium, но не наследует `gymnasium.Env`; в закрытом режиме терминальная награда равна `None`.
- Модули прототипа (`llm*`, `hf_*`, `rag*`, `tests_extras/`) пока написаны под первую предметную модель и в `verify` не входят.
